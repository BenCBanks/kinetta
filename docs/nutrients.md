# Extra nutrients and coverage

Workstream O is split into storage/source support, full logging-pipeline integration and phone controls. The first part adds nullable `sodium_mg`, `sugar_g` (total sugar) and `saturated_fat_g` fields to logged/custom foods and corresponding known recipe fields. It also adds optional `sodium_target_mg`, `sugar_target_g` and `saturated_fat_target_g` profile limits. They start unset. No calorie/protein target, watch source or energy algorithm changes.

Old records remain unknown for these nutrients; migration53 does not fill them with zero. A genuine reported zero remains a known zero. Bounds reject malformed/negative/nonfinite input and booleans; the validation caps are not intake recommendations. Total sugar is not treated as added sugar, and sodium is not displayed as salt.

Open Food Facts' normalized `_100g` quantities use grams for weight-based nutrients, including sodium. Kinetta converts sodium to milligrams once, while sugar and saturated fat remain grams. The contributor's separate `_unit` is not applied again to a normalized field. Absent, malformed or implausible values stay unknown without dropping otherwise usable calorie/macronutrient data. See [Open Food Facts' nutrition schema](https://openfoodfacts.github.io/documentation/docs/Product-Opener/schemas/schemas/product_nutrition/).

USDA mappings use sodium1093/307, total sugar2000 or1063/269, and total saturated fatty acids1258/606. Explicit g/mg/microgram units are converted; incompatible units are refused. When both total-sugar forms are supplied,2000 wins rather than adding them together or depending on response order. See [USDA FNDDS nutrient identifiers](https://www.ars.usda.gov/ARSUserFiles/80400530/pdf/fndds/2019_2020_FNDDS_Doc.pdf).

Authenticated food add/edit/copy/delete, saved-combination items and custom-food serving conversions preserve these fields. A same-unit amount edit scales existing known values when an older client does not supply them; an unconvertible unit change makes them unknown. Older custom-food forms preserve fields they do not know. Optional limits also survive older calorie/macro target forms, and clearing one requires an explicit null. Data download includes the new fields in JSON and the food CSV. Existing RLS/account ownership/deletion applies; no new personal table or provider is introduced.

The day API returns `extra_nutrients`: for each nutrient, a recorded subtotal (null if no values are known), known/unknown food counts, completeness, unit and optional limit. A partial subtotal is never marked complete intake. Empty days do not produce a zero-content statistic. Core calorie/macronutrient totals retain their existing contract.

Recipe ingredient/known totals, imported published values, portion logging, legacy explicit meal chat, thread manual/catalog/private learned foods, corrections, receipts, copy and Undo now carry all eight nutrient fields. Milligrams use their own bounds and scaling; values missing from an ingredient make that recipe nutrient unknown unless explicitly overridden. Calories-only recipes no longer invent zero macros. Old five-field recipe-review clients retain newly available published nutrients; explicit null clears a value, and review fingerprints preserve that distinction on Save.

Phone detail, collapsed daily totals and Overview now show these fields with known/missing food coverage. Daily limits are optional user-entered values, blank by default under Daily targets, saved only by its primary Save action. Range totals are labelled as recorded totals and are not compared with a daily limit. Manual label/recipe/food entry supports the three extras; portion changes and queued reuse preserve them. A tiny nonzero value is shown as below the display step rather than as zero. No new interface is enabled by the storage part. Existing AI photo/label schemas are unchanged; missing model output remains unknown. Any expanded recognition schema needs the reviewed evaluation process before enabling it. Tests use fictional source rows and throwaway accounts with no provider/model requests; they do not prove database coverage, label/OCR accuracy or a person's intake.
