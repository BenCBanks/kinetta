# Uncertain setting saves

A failed reply does not prove that a setting was rejected. The client keeps the layout and focus stable, neutralizes uncertain selection indicators, and visibly locks every save control on that surface until saved readback succeeds. Other settings retain their last confirmed presentation; inputs keep their drafts and focus. A sibling toggle or submit cannot display an unsaved choice or silently discard a second save. A compact status says “Not confirmed. Retry” (“Sharing not confirmed” on Sharing & privacy). It persists only an account/server-scoped expiry timestamp before dispatch. It waits 25 seconds from dispatch before reading back an uncertain setting: a 15-second client request wait, the eight-second server budget, and two seconds of margin. Retry reads the saved value without repeating the write; an early Retry shows “Checking…” and automatically fetches after the remaining window, without another tap. The status has a reserved row at the end of the surface, so it never covers a setting and does not shift rows when it appears. Controls re-enable after confirmation. The timestamp expires without a status request. Successful writes can be read back immediately. Ordinary API GETs are never gated.

Every matched setting write is bounded on the server, including older clients without special headers. The eight-second request budget starts when the application admits the request. Its absolute deadline follows endpoint threads and each `db.connect()` transaction. Pool acquisition waits at most one second; lock waits at most one second and statements at most two seconds. PostgreSQL 17's transaction timeout enforces the remaining request budget, including time between statements. An expired worker cannot open a new transaction, and the deadline is checked again before commit. No schema change or reservation endpoint is used.

Covered writes include profile/consent, account/profile presentation, activity audience/details, achievements, public cards, contacts, recipe sharing, leaderboards, memory preferences, groups/challenges and invitation membership. Saved values and reads remain authenticated and account-scoped. Group recap recovery awaits the reload; failed reloads keep values unconfirmed. The legacy group sharing action remains available.

Limits: this bounds work after server admission, not a request held upstream before admission. The client grace period assumes admission occurs within its transport wait; it is not an end-to-end network guarantee. It does not serialize simultaneous devices or reject every older request that arrives later. Other devices and legacy clients can change the saved value after a read; older clients do not gain the new unknown-state UI. Browser clock/storage failure, process suspension and physical-iPhone networking need device checks. No stronger ordering guarantee is claimed.

A read-only Retry retains the original requested change and write error. Readback is compared with the requested setting (including nested settings and normalised phone numbers): a different value shows “Not saved” beside the actual saved choice; a matching value confirms a committed request even if its reply was lost. The attempted change remains in memory until the next submission; it is never silently resubmitted. Same-account surface repaints retain rejection feedback. Retry returns focus to the original setting. Card settings use the shared focus-preserving lock; native input disabling is not used while saving.

Group invitations additionally retain the pending accept/decline action and sharing choice under a server/account/invitation-scoped local key, independently of the expiry timestamp. Both link and addressed routes restore that choice before checking whether to redirect. Reload within the grace period remains unconfirmed; after it expires, only GET reconciliation is allowed. Membership with a different saved sharing choice stays on recovery, showing the stored choice and the requested choice. Failed reads keep the choice; matching confirmation (or a definite not-joined state) clears it. Persisting the choice must succeed before a new write is sent. No password, session token or group content is stored in that key.
