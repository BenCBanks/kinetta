# Recipe link imports

Workstream N is split into a fetch/parser foundation and its authenticated review flow. The fetch/parser foundation is now used by an authenticated draft API; there is not yet a user-facing import action. It makes no AI calls and adds no dependencies or stored personal data. The review flow must authenticate, apply a per-person rate limit, and show an editable draft before any save or food log.

`recipe_fetch.fetch` accepts HTTPS URLs on port 443 only. It rejects credentials, local names and non-public addresses, including mixed public/private DNS answers and IPv6 transition routes. Each redirect is checked and resolved again. The socket connects to the validated IP while TLS certificate verification, SNI and the HTTP host retain the original hostname; DNS cannot change the destination between validation and connection. Environment proxies, cookies and authorization are not used.

Reads have a ten-second overall deadline, bounded DNS waits and workers, four concurrent fetch slots, three redirects and a one-MiB body limit. Compression and non-HTML responses are refused. A deadline timer closes the socket to limit trickling headers/body; socket and TLS operations also have bounded waits. Unreachable or unsupported pages return a short fallback message without exposing internal network errors. The HTML stays in memory and must never be persisted, logged or included in an AI request.

`recipe_schema.parse` reads bounded JSON-LD only, including arrays and `@graph`. It never executes scripts, follows linked schema nodes or downloads images. It returns at most five candidates, retaining names, ingredient strings, yield labels and published nutrient quantities. Instructions and the rest of the page are discarded. Text is treated as untrusted; consumers must render through text nodes rather than HTML.

Published nutrition is labelled as the site's per-serving information, not an AI estimate or a verified measurement. Units are converted explicitly (kJ to kcal, mg/mcg to g or mg). Missing, bare-unit or ambiguous numbers remain unknown; a published zero remains zero. Original nutrient text is retained for review. A clear serving count is preferred over yield units such as cookies; ambiguous yields require the person to supply servings. Published nutrients are never divided by the yield again. Multiple candidates require a choice, not silent selection.

The draft API requires login and an explicit read. Its per-person 30-attempt UTC-day cap counts failures and discarded attempts, serializes concurrent claims, and caches same-UUID retries without refetching. It stores parsed candidates and deterministic matches to the owner’s existing foods, never a saved recipe or food entry. No matching lookup uses another member’s records or a provider/model. A pending read can be discarded; its late result cannot restore it. Interrupted reads become failed rather than automatically retrying. Drafts expire after 24 hours; expired parsed content is cleared on the owner’s next read. Retry/cancellation identities remain private until account deletion. RLS, export and deletion apply; the AI SQL role has no access to this new table.

The review/save API now recalculates matches from the owner’s current foods. Review can edit the name, serving count, ingredient lines and per-serving numbers. It labels each nutrient as published by the site, summed from completely matched ingredients, entered, or unknown. Missing site values may use complete ingredient totals; partially matched ingredients never produce a partial whole-recipe sum. Keeping site values after editing ingredient lines carries an explicit original-recipe warning flag.

Save requires an explicit confirmation and the displayed review fingerprint. A changed own-food source returns a conflict for another review/tap. The recipe and saved-draft identity commit together; retry returns the existing recipe, even after later edits, and cannot recreate a deleted recipe. Parsed preview content clears on save; the saved recipe keeps only its structured recipe/source information. Saving does not log food.

Imported recipes store whole-batch known totals, nullable fiber, source metadata and their reviewed serving count. One serving logs one fraction of the whole batch; grams require a complete known batch weight or an explicit cooked weight. Unknown calories prevent logging. Missing macros remain marked unknown through portion logs and conversational matching. Existing ordinary recipes keep their prior whole-meal serving behavior.

The next slice adds the URL action and My Recipes draft review interface, with screenshots and optional unknown-ingredient resolution. Unknown ingredients may use the existing AI path only with consent and its existing release/budget gates. Missing structured data falls back to the recipe screenshot path. Fetching must happen only on an explicit import action, not on opening history or a tab.

Tests use fictional saved HTML and transport/DNS/TLS stand-ins; they make no external requests. They cover published/missing nutrition, odd units and yields, malformed/oversized/complex data, private addresses, DNS rebinding, redirects, deadlines, byte limits and resource cleanup. Browser screenshots belong to the subsequent UI slice. This foundation does not prove a particular recipe website is reachable or correctly publishes nutrition.

References: [Google Recipe structured data](https://developers.google.com/search/docs/appearance/structured-data/recipe), [schema.org NutritionInformation](https://schema.org/NutritionInformation), [Python HTTPSConnection](https://docs.python.org/3.12/library/http.client.html), [Python TLS](https://docs.python.org/3.12/library/ssl.html).

## Phone flow

My Recipes → Recipe from a link → paste → Read recipe → edit/check the draft → Review nutrition → Save recipe. Reading and reviewing never log food. The last Save is a separate explicit confirmation. A source-food change refreshes the review and requires another Save tap. A lost save acknowledgement retries the same draft identity, so it cannot save twice. Multiple recipe candidates require a choice. Imported recipes display per-serving values in the library and portion picker; their whole-batch yield remains visible.

The text draft and server identity are cached on the device under the selected server and numeric account ID, never an auth token. Reloading can recover the draft; switching accounts does not display or submit it for the other account. Account deletion removes that account's local recipe draft. No automatic URL fetch starts just because someone opens a tab or a draft: recovery reads the already parsed server draft only. Offline link text is retained for an explicit later read; saving is acknowledged only after the server confirms.

Site values stay labelled as published, entered values as entered, and missing values as unknown. Unmatched ingredients are optional when published site nutrition is being used; they do not trigger AI calls. An explicit estimate confirmation sends only that unmatched ingredient to the existing food estimator, with existing food consent/access/service budget controls. Known foods and published site values are not overwritten. The draft shows the assumed portion and marks any resulting ingredient totals as including AI estimates. Retries, cancellation and revoked consent cannot apply a late answer to a discarded/saved draft.

When structured recipe data is absent, a recipe screenshot uses the existing food-photo review and estimator but holds the result in a recipe draft. It requires food AI access/consent, a reviewed image selection and a user-entered serving count. It never auto-logs food. A published source is not invented for a screenshot: its numbers are AI estimates, with assumptions shown. No image is kept in the server draft or recipe; only the parsed estimate/source metadata remains. A private input hash binds photo retries without keeping the image. Selected screenshot pixels live in memory for the current view; choosing them again may be needed after closing it.

Known fiber can now be edited with the whole-recipe totals. Editing imported numbers changes their source labels to entered; using ingredient totals is explicit and remains conservative when some ingredients are unresolved. A count-only ingredient can be given its first actual weight without changing its known nutrition. Later weight changes scale its nutrition. A partial sum of ingredient weights is never offered as the whole recipe's weight.

Portion logging retains the existing offline queue, shows a pending cached food immediately and offers toast Undo with a visible light-haptic equivalent. Undo uses a durable owner-bound cancellation identity, so a queued upload or lost acknowledgement cannot restore the removed portion. It still works after the saved recipe is deleted. Queue persistence must succeed before the pending display is removed. UUID generation also works when the browser lacks `crypto.randomUUID`.
