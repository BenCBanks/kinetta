# Aggregate feature reports

Issue #444 adds Administration → Features. Its fixed queries return totals only; there is no account filter, free-form query or content drill-down. Existing-record counts reflect retained records, using UTC creation/acceptance/join dates, except weigh-ins use the recorded weigh-in day. Active plans, leaderboard opt-in and registered push devices are labelled current state. Food-source provenance is not a reliable logging-method history. Optional forward-only action labels on new food rows distinguish describe, search, barcode, photo, recipe, copy and manual actions; older rows/clients stay unknown. Labels are not added to model context or nutrition source references. They are immutable on nutrient edits and ignored on replay. Kit legacy rows are retained conversations, not a complete visit history.

Counts for fewer than three contributors are hidden before serialization, including uses/rates/comparisons. A trend is hidden if any bucket is small, so the total cannot reveal its remainder. Funnel counts also hide a complement smaller than three; steps are independent and week2 excludes immature cohorts. These controls reduce small-cell disclosure; they are not differential privacy or a guarantee of anonymity.

The hosted service has `KINETTA_FEATURE_METRICS=1` enabled (owner decision, 25 November 2026) for all accounts. There is no individual opt-in or withdrawal control. Self-hosted installations remain off unless their operator sets the variable to `1`. The feature report uses a fixed feature enum and account authorization; it does not collect URLs or free-form text. The service uses a daily random key to derive temporary feature-specific account digests for updating aggregate counters, then removes the key and digests. Food-entry methods are stored as account-linked action labels on new food records; they are not added to AI context or nutrition references. Record reports and the signup cohort include all retained accounts. Setup steps completed before collection began remain unknown. Review `site/content/privacy.md` and generated `site/privacy.html` alongside the release disclosures below. This documentation update does not change a runtime setting.

Authenticated opens carry one fixed feature enum, never a URL, account ID or text. The backend supplies the owner and UTC day. A daily random key produces feature-specific HMAC digests. The key and digests are limited to the current UTC day and cleared after midnight by collection/read cleanup and a worker that runs every minute. The anonymous `(feature, day, people, opens)` counters retain13 calendar months, without identifiers. Repeat opens are coalesced for30seconds. Successful counter requests bypass account-linked API diagnostics; failed requests and other API diagnostics retain their existing behavior. Across days, sums are labelled user-days from visible days only; hidden days never contribute to public report sums. A previous12-month comparison is unavailable with13-month retention.

First welcome completion and Health permission-screen completion store only a UTC day on the existing private profile, cleared on account deletion. Historical setup is unavailable and never backfilled. Health setup does not prove that Apple allowed any read category. Anonymous daily totals cannot be linked back to a deleted account and remain until expiry. New admin counter/key/state tables enable RLS and grant no reader access.


## App Store release requirements

For the submitted build, App Store Connect should classify Usage Data → Product Interaction as used for Analytics and linked to the user. User ID, Health and Fitness also include Analytics alongside App Functionality. Authentication, temporary matching keys and account-linked setup/action labels mean this collection cannot be described as entirely unlinked. Health/Fitness records are used to derive counts, although raw health readings, route geometry and private text are not included in the aggregate reports. The bundled manifest declares these Analytics purposes. Confirm the actual Connect answers before submission; this documentation update does not change them or runtime settings.

Apple defines these categories and linking in [App privacy details](https://developer.apple.com/app-store/app-privacy-details/), sets data-collection requirements in [Review Guideline5.1.1](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage), and allows [privacy-answer updates](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy) without submitting a new binary. The operator switch applies to all accounts; it is not a per-person permission control. First-party analytics alone does not invoke Apple's cross-company advertising tracking definition. No Apple approval is claimed.

The owner chose all-account collection without a per-person control. That choice and the disclosure taxonomy do not establish an exception to Apple’s consent/withdrawal, repurposing or HealthKit requirements under [Guidelines5.1.1–5.1.3](https://developer.apple.com/app-store/review/guidelines/#privacy). Reconcile those requirements during release review; this change does not claim Apple acceptance.
