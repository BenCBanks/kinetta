# Bounded own-data comparison helper

`OwnComparison(authenticated_user_id).read(arguments)` is a deterministic application helper, not a registered model tool or public endpoint. The caller binds identity; `arguments` cannot contain a user ID, connection, SQL or arbitrary expression. It introduces no provider calls and does not authorize generation: callers still enforce current AI/access/18+/email/release/budget checks.

Arguments are `start`, `end`, one metric (`workouts`, `distance_m`, `duration_s`, `protein_g`) and an optional workout `sport`. Both equal-length periods use completed account-local dates; each has at most 366 inclusive dates. The prior period ends the day before `start`. Sport is a bounded parameter and is rejected for food comparisons. Current/future days and calendar underflow are rejected.

The helper uses `db.coach_connect`: fixed SQL, explicit owner predicates, read-only RLS and a statement timeout. It aggregates the full period, without listing or limiting raw activity rows. Unfinished lifting is excluded. Health-derived activities require `health_ai_ok`, including manual records with a Health identifier. Garmin records require `garmin_ai_ok`. Mixed provenance requires both. Denied sources are filtered before aggregation; their rows, names and counts are not returned. Health-derived weight consent is not required because this helper does not read weights or body settings.

Results contain `metric`, `sport`, `timezone`, `source_consents`, `current`, `previous`, `change` and limitations. Each period includes exact dates, calendar days, `value`, `known_total`, record and missing-measurement counts, food logged days and elapsed-time fallbacks. Missing/invalid measurements remain unknown. Protein requires known values on every calendar day; even complete daily logging can understate intake. Zero recorded workouts means zero recorded workouts, not proof of inactivity. A zero baseline has no percentage change.

`source_consents` describes permission scope, not which denied sources exist. The helper discards a workout result if either source consent changes during the read. Before passing any derived result to a provider or saving it, a future integration must revalidate applicable consent and bind that check to the result's source scope; no database read can prevent a revocation after its last query. Do not bypass existing other-tool or saved-context consent gates. Model integration and its reviewed evaluation/fingerprint are separate work.

Disposable-database contracts cover source combinations and mixed provenance, independent weight consent, owner/RLS/read-only boundaries, complete aggregation beyond a page, unknown flags/nonfinite values, sparse food logs, zero baselines, elapsed fallback, leap/DST dates, bounds/forged arguments, in-flight consent changes and no provider calls. These are deterministic contract checks, not model-quality evidence.
