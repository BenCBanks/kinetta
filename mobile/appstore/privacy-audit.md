### Current Kit, achievements and Health data flows (13 November 2026)

A meal-chat message may contain both food and an explicit weigh-in. The server parses the weight deterministically, presents food and weight together for review, and writes the confirmed weigh-in to the account-linked weight store only when the person confirms it. This structured weight path works with AI disabled; the chat message and review choices remain account-linked user content. Sources: `app/food_thread_weight.py`, `app/food_thread_log.py`, `app/food_thread_compose.py`, `app/api_food.py`.

Apple Health workout import and body-weight import are separate permissioned reads. Imported workout records are account-linked Fitness data; optional body mass becomes an account-linked Health/weight record. Kinetta receives only data HealthKit returns for allowed categories. Sources: native `HealthBackgroundSync.swift` and `HealthFood.swift`, `app/api_activities.py`, `app/api_health_weights.py`.

The achievement ladder calculates named sport levels from saved workout and training records. Those derived levels remain account-linked Fitness data; any sharing follows the separate achievement-sharing choice. They do not add a separate data type. Sources: `app/achievement_tracks.py`, `app/api_achievements.py`, `app/static/profile.achievement-levels.json`.

The manifest includes this conservative inventory. Retain existing Health/Fitness/User ID Analytics purposes: feature reports inspect Health-sourced workouts and weight/food counts. **Collection is operator-controlled for all accounts, not per-person opt-in**. It is reported OFF in the issue's release record; source review does not verify today's live switch. Before enabling, the owner must resolve Guideline5.1.3 Health-data analytics eligibility (or exclude those sources and revise disclosures) and collection/consent requirements. Do not infer Apple approval from aggregation. See [review guidelines](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research) and `docs/admin-features.md`.

## Optional iPhone contact matching

The native bridge reads Contacts only after the person chooses “Continue” and grants iOS Contacts access; iOS limited access is supported (`mobile/ios/App/App/NativeContacts.swift`, `app/static/contacts-ui.js`). It reads the system contact identifier, given/family names, email addresses and phone numbers. The local hasher normalizes email and phone values and returns at most 2,000 per-check, type-tagged salted SHA-256 digests (`mobile/ios/App/ContactMatchCore/Sources/ContactMatchCore/ContactMatchHasher.swift`). Names, raw email/phone values and local identifiers are not in the `/api/contacts/match` request. That request contains the fresh salt and `{kind, digest}` entries; the reply contains only submitted digests that matched plus the account’s public login (`app/api_contacts.py`).

The device maps returned digests to names and contact IDs in memory. Its `localStorage` match cache stores only matched `{contactId, login}` rows and a timestamp, scoped by server and signed-in account (`app/static/contacts-ui.js`, `app/static/app.js`). The “Remove my contacts” action deletes that cache key; it does not delete the phone’s address book or the account’s email/phone. The caller checks OS permission before reading; the code does not show that revoking permission automatically clears a previously saved match cache. In Me → Settings → Sharing & privacy, the person can turn off email/phone discoverability; the server then excludes that account from the corresponding match. Turning off either switch does not delete the account email or phone. Clearing the optional phone field sends `phone_e164: null` and removes it from `users.phone_e164` (`app/static/social.js`, `app/api_contacts.py`).

The matching endpoint explicitly avoids logging or persisting its request body. It does persist a per-account 24-hour rate-limit attempt row in `auth_attempts`; cleanup deletes rows older than one day (`app/api_contacts.py`, `app/account_email.py`). This source review does not establish retention in every proxy or host log. Salted SHA-256 is not private-set-intersection: the source warns that low-entropy email/phone values can be guessed if a hash and salt are captured. The current native manifest labels Contacts unlinked and Phone Number linked, both for App Functionality (`mobile/ios/App/App/PrivacyInfo.xcprivacy`). The exact Apple classification of the transmitted salted contact hashes needs owner confirmation before entering App Store Connect; this docs-only change does not alter the manifest or Connect answers.

## Providers and exclusions

Kit requires18+ eligibility, the person's AI opt-in and reviewed server gates (`app/ai_access.py`, `app/ai_release.py`). Health/Garmin inclusion additionally requires its specific consent. Authenticated tools supply only relevant own records (`app/kit_tools.py`, `app/coach_chat.py`); food estimates can send descriptions, photos and selected private context (`app/food_photo.py`, `app/food_memory_understand.py`). The meal-chat weight parser is code-only and does not call an AI provider; confirmation still gates persistent food and weight writes. Review/confirmation still gates AI-proposed writes. Never claim AI accuracy from these contract checks.

`app/ai_release.py` defaults: food Gemini `gemini-3.1-flash-lite`, fallback `gemini-3.8-flash`; coach Gemini `gemini-3.8-flash`, fallback `gemini-3.1-flash-lite`. `app/coach.py` also supports configured Anthropic `claude-opus-5-5`. Environment overrides and reviewed feature gates determine the actual release. The policy names both providers and links their retention terms. Do not claim zero provider retention or declare only Google without the owner checking the submitted configuration. P above covers tailored suggestions even though ordinary food estimation is F.

Maps: `app/static/maps.js`/`app/map_config.py` request configured map tiles/file ranges; the hosted policy describes Cloudflare/R2 processing network addresses and viewed areas without account cookies or workout times. Location is already declared. Unsaved GPS samples are not uploaded as workout records; configured map requests still disclose viewed areas. Saved recordings are uploaded. USDA/Open Food Facts receive queries/barcodes; recipe import fetches a supplied public URL without account credentials (`app/api_food.py`, `app/recipe_import.py`). Imported recipe source URLs persist as user content, not a general browsing-history tracker. Mail receives addresses and message contents; Apple delivers optional push (`app/account_email.py`, `app/notify.py`). Review configured partners' retention before submission.

No crash-reporting or third-party analytics SDK appears in `mobile/package.json` or the native dependency list. No automatic crash dump, microphone recording, payment, advertising identifier or medical-record import is implemented. Server exception/status logs are operational diagnostics, not evidence of native crash collection. Free-form notes can contain sensitive subjects; Apple instructs generic fields to use Other User Content, rather than inventing every possible category. No dedicated sensitive-category prompt exists. Recheck if dependencies, recording or data flows change.
